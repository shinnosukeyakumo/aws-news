# ニュースサイト化の設計

Discord への配信をやめ、選別・要約した記事をスマホで読めるニュースサイトとして公開する。
サイトは定期的に自動で更新される。認証は 2026-11-21 に外した（下の「4. 認証」）。

状態: 実装済み。2026-11-03 に ap-northeast-1 へデプロイし、手動実行でサイトの生成と Basic 認証を確認した。

2026-11-21 に画面を作り直し、検証の機能を外した。下の「ニュースだけにし、マイライブラリを足す（2026-11-21）」が今の形だ。
2026-11-14 の「点数をやめ、通知と検証を一画面に」と、それより前の点数・種類のタブ・`min_score` の話は経緯として残している。

## 目的と前提

- Discord や Slack の埋め込みは幅が狭く、スマホで読みにくい。1 記事を 1 枚のカードとして読める画面にする
- Mac を閉じていても更新が止まらないよう、実行も配信も AWS 上で完結させる
- 閲覧者は自分 1 人。当初は URL を知られただけで読める状態にはしない方針だったが、2026-11-21 に認証を外した
- 収集・採点のロジック（`collect.py` / `curator.py` / `config/sources.yaml`）は変えない。変えるのは「結果をどこに溜め、どう見せるか」だけ

## 全体の流れ

```
EventBridge Scheduler（毎日 9:00 / 18:00 JST）
  └→ Lambda（コンテナイメージ）
       1. 情報源から記事を集める                 … collect.py（既存）
       2. 既読を DynamoDB で除外する             … store.py（置き換え）
       3. Bedrock（Nova 2 Lite）で採点・要約する … curator.py（既存）
       4. 採点結果を DynamoDB に書く
       5. 直近 30 日分を DynamoDB から読み、HTML を組み立てる … site.py（新規）
       6. HTML と JSON を S3 に置く
S3（非公開） ←OAC─ CloudFront ←HTTPS─ スマホ
                      └ 認証なし（2026-11-21 に Basic 認証を外した）
```

採点（1〜4）とサイト生成（5〜6）を分けておく。
採点が一部失敗しても、DynamoDB に溜まっている分からサイトは作り直せる。

## 構成要素

### 1. 実行: Lambda（コンテナイメージ）+ EventBridge Scheduler

| 項目 | 値 | 理由 |
|---|---|---|
| ランタイム | Python 3.12 のコンテナイメージ（arm64） | `uv.lock` をそのまま使って依存を固定できる |
| メモリ | 1024 MB | 本文取得と 4 並列の Bedrock 呼び出しが主。CPU はほぼ使わない |
| タイムアウト | 15 分（上限） | 3 エージェント × 最大 12 件。Nova は 1 件 4 秒前後なので通常は 1〜2 分で終わる見込み |
| 再試行 | 0 回 | 失敗時に自動で再実行すると、Bedrock の呼び出しが二重になる。次の定期実行に任せる |
| スケジュール | `cron(0 9,18 * * ? *)`、タイムゾーン `Asia/Tokyo` | 現行 README の cron と同じ時刻 |

zip ではなくコンテナを選んだ理由: 依存の実サイズは 73 MB で、zip の上限（展開後 250 MB）にも収まる。
ただし CDK で zip を作る場合もビルドに Docker が要る。それなら `uv.lock` をそのまま使えるコンテナのほうが、ローカルと Lambda で依存がずれにくい。

### 2. データ: DynamoDB

SQLite（`data/seen.db`）は Lambda に置けないので DynamoDB に移す。
既読の記録だけでなく、採点結果の本文（見出し・要約・効き目など）もここに溜め、サイトの材料にする。

テーブル `articles`（オンデマンド課金）

| 属性 | 例 | 用途 |
|---|---|---|
| `pk`（パーティションキー） | `aws-ai` | エージェントの key |
| `sk`（ソートキー） | 記事 URL | 既読判定。同じ URL でもエージェントが違えば別扱い（現行の SQLite と同じ） |
| `feed` | `all`（固定値） | 下記 GSI 用 |
| `sort_at` | `2026-09-25T00:00:00+00:00` | 公開日。無ければ採点した日時 |
| `score` / `title_ja` / `summary` / `impact` / `reason` / `tags` | | 採点結果。`Curation` モデルと同じ |
| `title_original` / `source_label` / `published_at` | | 元記事の情報 |
| `status` | `curated` / `failed` | 採点に失敗した記事も記録し、再挑戦させない（現行と同じ扱い） |

GSI `by-date`（パーティションキー `feed`、ソートキー `sort_at`）で「全エージェントの新しい順」を 1 回の Query で取る。
記事は月に数百件の規模なので、パーティションを 1 つに寄せても負荷の問題は起きない。

ローカル開発では SQLite を使い続ける。`store.py` に共通のインターフェースを切り、SQLite 版と DynamoDB 版を差し替えられるようにする。

### 3. 配信: S3 + CloudFront

- S3 バケットは非公開。CloudFront から OAC（Origin Access Control）経由でだけ読ませる
- 置くファイルは `index.html`（直近 30 日）と `articles.json`（同じ内容のデータ）
- HTML は `Cache-Control: max-age=60`。更新は 1 日 2 回なので、キャッシュ削除（invalidation）を使わず短い TTL で済ませる
- ドメインは CloudFront の既定（`*.cloudfront.net`）。独自ドメインは今回は付けない

### 4. 認証: CloudFront Functions の Basic 認証（2026-11-21 に外した）

2026-11-21 に八雲が「めんどいから認証機能はいらない」と決め、Basic 認証の関数と KeyValueStore を外した。
載せているのは公開ニュースの要約だけなので、読まれても困らない。
代わりに `/api/library` と `/api/settings` は URL を知る人なら誰でも書き換えられる。書ける先は articles テーブルの `pk="#settings"` の 2 項目だけで、記事そのものは書き換えられない（IAM の LeadingKeys 条件）。
荒らされたら、ブラウザ側の localStorage に同じ内容が残っているので、保存し直せば戻る。

以下は外す前の検討。

| 案 | 採否 | 理由 |
|---|---|---|
| CloudFront Functions で Basic 認証 | 採用 | 追加のサーバーが要らない。ブラウザがパスワードを覚えるので、2 回目以降は開くだけ |
| Cognito + Lambda@Edge | 不採用 | ログイン画面とトークン更新まで作ることになり、1 人用には重い |
| URL に秘密の文字列を付ける | 不採用 | 閲覧履歴や共有時に漏れる |

パスワードはコードにも CDK にも書かない。

- 正解の値（`ユーザー名:パスワード` の Base64）は CloudFront KeyValueStore に入れ、関数はそこから読む
- 値はデプロイ後に CLI で登録する。パスワード本体は 1Password に保管する
- CloudFront は HTTP を HTTPS にリダイレクトする設定にし、平文で認証情報が流れないようにする

未確認の点: iPhone の Safari が Basic 認証の入力をどこまで覚えてくれるか。
毎回聞かれて煩わしい場合は、初回だけ認証して長期間有効な Cookie を発行する方式に切り替える。実装後に実機で確かめる。

### 5. 画面

1 列のカードを新しい順に並べる。スマホ幅を基準に作り、PC では中央寄せにする。
見本（9/6 の実データ 40 件、振り分けは手で付けた仮のもの）を Artifact に置いてある。

```
┌──────────────────────────┐
│ aws-news     最終更新 9/6 09:00 │ ← 更新が止まったら気づけるように
│ [すべて][実装・設計][AWS 新機能] │
│ [事例]  [動向]     [新モデル]    │ ← 記事の種類のタブ（3 個ずつ 2 段）
├──────────────────────────┤
│ (Amazon Bedrock 13)(AgentCore 6) │ ← タグの帯（ヘッダーの外。横スクロール）
│ 9/4（木）                      │
│ 75 実装向け  実装・設計 AWS AI Blog│
│ AgentCore のメモリ…設計 ↗        │ ← 日本語の見出し（元記事へのリンク）
│ 原題                           │
│ 要約 2 文                      │
│ 効き目 1 文                    │
│ [AgentCore][Step Functions]     │ ← タップで絞り込み
├──────────────────────────┤
│ …                            │
└──────────────────────────┘
  見送った記事 ○ 件（55 点未満） ▾  ← 畳んでおく。採点の理由が読める
```

#### タブ: 記事の種類で分ける

担当エージェント（媒体）ではなく、記事の中身で分ける。媒体が違っても、新モデルの発表は同じタブに並ぶ。

| タブ（並び順） | 中身 | 9/6 の 40 件での件数 |
|---|---|---|
| すべて | 全部 | 40 |
| 実装・設計 | 作り方、構成、移行の手順、ベストプラクティス | 12 |
| AWS 新機能 | AWS のサービス・機能・リージョンの追加 | 6 |
| 事例 | 企業が AI を導入した話 | 9 |
| 動向 | 安全性、規制、資金、業界の動き | 6 |
| 新モデル・製品 | AWS 以外のモデルや製品の発表 | 7 |

- 並びは読む優先度の順にする。新モデル・製品は注目度が高くないため一番右に置く
- タブは 3 個ずつ 2 段に並べ、全部を常に見せる。横一列だとスマホ幅で右側が画面の外に隠れ、隠れていることに気づけないため
- 2 段で高くなったヘッダーの代わりに、タグの帯はヘッダーの外に出し、スクロールで流れる位置に置く
- タブでは「新モデル・製品」を「新モデル」と縮めて表示する。カードには正式な名前を出す
- 種類は採点と同じ呼び出しでエージェントに答えさせる（`Curation` に `category` 欄を足す）。Bedrock の呼び出し回数は増えない
- 種類の一覧と判定基準は `sources.yaml` に書き、タブもそこから作る
- Nova が手の振り分けと同じように分けられるかは未確認。実装後に 9/6 の 40 件で突き合わせる

#### タグで絞り込む

- タブの下に、今のタブで 2 件以上出てくるタグを件数付きで並べる
- カードのタグか帯のタグをタップすると、**今のタブの中で**そのタグの記事に絞る（「すべて」には移動しない）
- タグは複数選べる。選んだタグをすべて含む記事に絞る（AND）。帯には、今の絞り込みと組み合わせて 1 件以上出るタグだけを残す
- 絞り込んだまま別のタブに移ると、移った先のタブで同じ絞り込みがかかる
- タグの表記揺れは、`sources.yaml` に置く「正式名と別名の対応表」で採点のあとに機械的に揃える（例: AWS Bedrock → Amazon Bedrock）。表にない新製品も付けられるよう、タグの選択肢は固定しない

#### ウォッチ

- Bedrock・AgentCore・Strands のように、追い続けたい言葉を `sources.yaml` の `watch` に並べる。タグか題名にその言葉が入った記事を「ウォッチ」の欄に集める
- **点数とタブは問わない**。種類のタブで分けると Bedrock の記事が 5 つのタブに散らばり（9/6 の 40 件では 18 件が 5 タブに分散）、閾値未満の記事は畳まれて見落とすため
- 見出し・日付・当たった言葉・種類・点数だけを新しい順に並べる。55 点未満の記事も載せ、点数を薄くする
- 欄の中で言葉ごとに絞り込める。前回開いたあとに入った記事には「新」を付け、件数も出す（前回の時刻は端末に覚えておく）
- 置き場所: スマホは「すべて」タブの一番上に 5 件まで（タグで絞り込んでいる間は出さない）。PC は左の柱のタブの下に 8 件まで常に出す。どちらも「残りも見る」で全部開く
- `watch` の言葉は、のちに通知（Slack / LINE）を送る条件にもそのまま使う。ウォッチに当たり、かつ必読の記事を通知の対象にする想定
- 当たり方は正規表現で書く。「Amazon Bedrock AgentCore」が Bedrock にも当たらないよう、Bedrock は `Bedrock(?! AgentCore)` にしている

#### 閾値

- `min_score` は 55 にする（これまでは 80）
- 80 以上は評価基準の上で「新機能・新モデルの発表」の帯であり、実装の解説記事は最高でも 79 点になる。80 のままだと AgentCore の設計記事などが全部畳まれていた
- 種類はタブで分けたので、点数は「畳むほど価値が薄いか」の判定と、同じ日の中の並び順にだけ使う

#### 見た目

- サイト名は「AWS News」。`sources.yaml` の `site.title` で変えられる（2026-11-14 に「霜報」から変更）
- キャラクターの雰囲気は持ち込まず、普通のニュースアプリの見た目にする（2026-11-14 決定）。画面の文言はです・ます調
- **デプロイ版にはイラストもキャラクターにちなんだ飾りも入れない**（2026-11-03 決定）。権利の扱いで揉める種を残さないため。画面見本（Artifact）で試した星見雅（ゼンレスゾーンゼロ）の公式イラストは、見本の中だけにとどめる
- 地は白と灰色（ダークモードは黒）、文字は OS 標準のゴシック体。Web フォントは読み込まない。一覧の点数は角丸の枠
- トップ記事の上半分は、記事の種類の色を濃くした地に点数を大きく載せる。文字は白なので、明暗どちらのモードでも地の色は濃いまま固定する
- トップ記事は、必読があれば必読を先に出す。その次はタブの並び順（実装・設計が先）で選ぶ。点数だけで選ぶと新モデルの発表が上に来てしまうため
- 閾値未満の記事は「点数の低い記事」として一番下に畳む

#### PC（横幅 960px 以上）

- 頭の帯を画面幅いっぱいに広げる
- 左に柱を置き、タブを縦に並べ、その下にタグを折り返して最大 24 個並べる。柱はスクロールしても残る
- トップ記事は左に絵、右に見出し・要約・効き目の横長にする
- 一覧は日付ごとに 2 列のカードで並べる

#### 重要度の段階

| 点数 | 段階 | 中身 |
|---|---|---|
| 90〜100 | 必読 | 読まないと自分の実装や運用に支障が出るもの（破壊的変更、提供終了、セキュリティ修正、日々使う道具の大きな機能追加） |
| 80〜89 | 要注目 | 設計の選択を変えうる新機能や知見 |
| 55〜79 | 実装向け | 再利用できる具体的な情報 |
| 30〜54 | 限定的 | 特定の業界や用途に閉じたもの |
| 0〜29 | 参考 | 事例紹介、宣伝 |

- 必読は点数の枠を塗りつぶして目立たせる
- 段階の定義は `sources.yaml` の `tiers` に書き、全エージェントの system prompt に入れる。新モデルの発表は 89 点を上限にした
- 旧基準は 80〜100 を一つの帯にしており、新モデルの発表もそこに入っていた。9/6 の 40 件では 90 点以上が GPT-6 Astra の発表 1 件だけだった
- 新基準で直近 7 日の 25 件（2026-10-27〜11-03）を採点し直した。9/6 の 40 件は RSS から消えていて取り直せなかった
  - 必読は「AgentCore でエージェントが構築するウェブアプリをライブプレビュー」（90）の 1 件。新モデルの発表（Gemini 4 など）は 80 で要注目にとどまった
  - 点数は 90 / 80 / 75 / 55 / 30 / 20 に固まった。Nova が帯の境界に張り付く癖は変わらない
  - 「AWS Batch が SageMaker のクォータ管理に対応」が AWS 新機能ではなく実装・設計に入るなど、種類の判定には揺れがある

#### その他

- スコアの色分けは既存の `dashboard.py` の 4 段階（要注目 / 実装向け / 限定的 / 参考）を流用する
- ダークモードに対応する（`prefers-color-scheme`）
- 最後に開いたタブは端末に覚えておく

HTML は Lambda 側で完成させてから置く（サーバー側で組み立てる方式）。
ブラウザ側で JSON を読んで描画する方式より、スマホでの表示が速く、仕組みも単純になる。
タブとタグの絞り込みは、ページに埋め込んだ記事データを JavaScript で切り替える。

## ニュースだけにし、マイライブラリを足す（2026-11-21）

agentcore-playground に検証を頼む機能（「検証する」ボタン、「検証」タブ、`/api/verify`、テーブル `aws-news-verify-requests`）を外した。
aws-news はニュースを読むことだけに絞る。テーブルは RETAIN だったので、スタックから外しても AWS 上には残る（消すかは別に決める）。

画面は、ニュースを素早くふるい分けて、気になったものを手元に残す形にした。

- **カテゴリ（18 分類）で切る。** 要約のときにモデルが `category` を 1 つ付ける（先頭のタグのサービスのカテゴリ）。持たない古い記事は `categories.guess` がタグの正規表現から当てる
- **注目度（`importance`、1〜3）を付ける。** 点数をやめた理由（Nova が境界に張り付く）があるので、3 段階に留め、控えめに付けさせる。expansion と howto は原則 1。一覧は注目度順にも並べ替えられ、絞り込みで「★2 以上」のように使う
- **国内リージョン（`jp_regions`）を付ける。** 東京・大阪で使えるかを本文の記述から判断する。記述が無ければ `unknown`。カードには東京で使えるときだけ印を出す
- **期間は日本時間の暦で切る。** 今週 / 先週 / 今月 / 先月 / すべて。週は月曜はじまり。掲載は直近 60 日（`site.days`）
- **詳細は一覧の横に出す。** PC（1024px 以上）は右の欄、スマホは全画面。`j` / `k` で前後の記事に移る
- **マイライブラリ。** お気に入り（カテゴリ `c:<key>` かサービス `s:<名前>`）、保存した記事、保存した絞り込み条件の 3 つ。お気に入りはカテゴリのタブの先頭に出る。保存した記事は要約ごと写して持つので、掲載期間を過ぎても読める

マイライブラリは localStorage に持ち、AWS 上のサイトでは `/api/library` にも丸ごと置く。
articles テーブルの `pk="#settings", sk="library"` の 1 項目で、使うのは自分 1 人なので項目ごとの結合はせず、
`updated_at` が新しい方で上書きする。端末で変えたまま送れていない分（`dirty`）があり、それがサーバーより新しければ端末側を送る。
1 項目 400KB の上限に収めるため、保存した記事は 500 件、お気に入りは 50、条件は 30 までにしている。

古い記事の埋め戻しは、Curator の Lambda に `{"recurate_days": N, "limit": M}` を渡して手で回す。
`importance` を持たない記事だけを、記事ページを取り直して要約し直す。同じ記事を二度やらないので、`targets` が 0 になるまで繰り返せばよい。

受け口（`awsnews.api.handler`、`/api/*`）

| メソッドとパス | 中身 | 権限 |
|---|---|---|
| `GET /api/library` | マイライブラリ | articles の GetItem |
| `POST /api/library` | マイライブラリを丸ごと置き換える | articles の PutItem |
| `GET /api/settings` | 通知するサービスと種類 | articles の GetItem |
| `POST /api/settings` | 通知するサービスと種類を置き換える | articles の PutItem |

権限はどれも `dynamodb:LeadingKeys` で `#settings` に限る。受け口の Lambda は Curator と同じイメージで、入口（CMD）だけ替える。
OAC 経由で Lambda に POST するときは、本文の SHA-256 を `x-amz-content-sha256` ヘッダーで送る決まりがある。ページの JS が計算して付ける。

## 点数をやめ、通知と検証を一画面に（2026-11-14、検証は 2026-11-21 に外した）

点数を付けても、Nova は帯の境界に張り付いて判別が粗く、結局は全部の見出しに目を通していた。
そこで点数付けをやめ、全部を一覧に出したうえで「どのサービスの記事を手元に届けるか」を自分で選ぶ形にした。

- **情報源は AWS に絞る。** What's New（AI 以外も含む全サービス）と AWS の AI ブログの 2 担当。LLM ベンダー担当（`llm-vendors`）は外した
- **エージェントは要約だけをする。** `Curation` から `score` / `reason` / `category` を外し、`tags` に主題の AWS サービスを正式名で最大 3 つ挙げさせる。通知の要否はこのタグで決まる
- **通知は AWS サービス単位で選ぶ。** サイト右上の「通知設定」で選び、articles テーブルの `pk=#settings, sk=notify` に置く。この pk はエージェントの key と重ならず、`feed` 属性も持たないので、既読判定にも一覧にも混ざらない。未設定なら `site.notify_default`
- **通知先は Slack（Incoming Webhook）。** 1 回の実行で当たった新着を 1 通にまとめる（最大 20 件、超えた分は件数だけ）。URL は Secrets Manager の `aws-news/slack-webhook` に置き、`https://hooks.slack.com/` で始まらない値（CDK が作った直後のランダム値）のあいだは送らない
- **What's New の上限は 60 件。** 平日 10〜20 件（2026-11-14 に RSS で数えた）。re:Invent の時期は 1 日 100 件を超えるが、あふれた分は次の回に回る
- **検証と下書きは playground が作り、aws-news は見せるだけ。** 「1 つのアプリ」は画面を 1 つにする意味で、検証の実行場所は agentcore-playground のまま。記録と下書きは verify-requests に書き戻してもらう（上の表の `result` / `note_md` / `draft_md` / `has_draft`）

画面

- タブは「すべて / 新機能 / AI ブログ / 通知対象 / 検証」。「通知対象」は通知するサービスのどれかをタグに持つ記事
- トップ記事は、通知対象の最新。無ければ全体の最新。上半分には点数の代わりにサービス名を大きく出す
- 「検証」タブは承認した記事の状態と結果を並べ、終わったものは「記録を読む」「下書きを読む」で本文をダイアログに出す。下書きはコピーして Qiita に貼る想定なので、Markdown を描画せずそのまま出す
- 通知設定のダイアログは、上に記事の種類、下に直近の記事に出てきたサービスを件数つきで並べる。サービスは名前で絞り込める
- 点数や種類を持った古い記録が DynamoDB に残っていても、画面は読み捨てる。`llm-vendors` の記事は出さない

受け口（`awsnews.api.handler`、`/api/*`）

| メソッドとパス | 中身 | 権限 |
|---|---|---|
| `POST /api/verify` | 記事を承認する | articles の GetItem、verify-requests の PutItem |
| `GET /api/verify` | 承認した記事の一覧（本文を除く） | verify-requests の Scan |
| `GET /api/verify/{id}` | 記録と下書き | verify-requests の GetItem |
| `GET /api/settings` | 通知するサービスと種類 | articles の GetItem |
| `POST /api/settings` | 通知するサービスと種類を置き換える | articles の PutItem（`dynamodb:LeadingKeys` で `#settings` に限る） |

## 記事の種類で通知を絞る（2026-11-14）

サービス単位で選ぶだけでは、Bedrock の「東京リージョンに対応」も通知されてしまう。
また re:Invent で発表される AI の新サービスは、名前がまだ通知のリストに無いので届かない。
そこで要約のときに、モデルに次の 2 つも付けさせる。

- `kind`：`new_service`（新サービス）/ `feature`（新機能）/ `expansion`（リージョン・インスタンスなどの追加）/ `howto`（解説・事例）/ `other`（料金・その他）
- `generative_ai`：生成 AI・LLM・AI エージェントに関わる記事か

通知の条件は「選んだサービスをタグに持ち、かつ選んだ種類」または「`new_service` かつ `generative_ai`」。
種類の初期値は `new_service` と `feature`。種類が付く前に要約した記事は、サイトではサービス名だけで判断する。

Nova 2 Lite で直近の What's New 40 件ほどと AI ブログ 16 件を分類させて確かめた（2026-11-14）。
What's New はリージョンとインスタンスの追加が `expansion`、機能追加が `feature` に分かれた。
AI ブログは初め解説記事まで `feature` にしたため、「その記事で初めて発表しているのでなければ `howto`」と指示を足した。
足したあとは 10 件中 8 件が `howto` になった。

## AWS リソース

デプロイ先は `default` プロファイルのアカウント、リージョンは `ap-northeast-1`（東京）。Bedrock も `jp.amazon.nova-2-lite-v1:0`（東京・大阪で処理）で東京から呼ぶ。2026-11-03 に東京から `converse` が通ることを確認した。CloudFront と CloudFront Functions はリージョンを持たない。

| リソース | 主な設定 |
|---|---|
| DynamoDB テーブル | オンデマンド、GSI `by-date`、ポイントインタイムリカバリ有効 |
| S3 バケット | パブリックアクセス全ブロック、SSE-S3 |
| CloudFront ディストリビューション | OAC、HTTPS リダイレクト（認証は 2026-11-21 に外した） |
| Lambda 関数 | コンテナイメージ、arm64、1024 MB、15 分 |
| EventBridge Scheduler | 1 日 2 回、`Asia/Tokyo`。re:Invent の前後だけ、9 時・18 時以外の毎時を足して 1 時間おき（2026-11-21 に 3 時間おきから変更）（期間は `infra/stack.py` の `REINVENT_START` / `REINVENT_END`。毎年書き換える） |
| IAM ロール（Lambda 用） | 下記の最小権限 |

Lambda に渡す権限

- `bedrock:InvokeModel` / `bedrock:InvokeModelWithResponseStream`: Nova 2 Lite の推論プロファイルと、その転送先リージョンの基盤モデルに限定
- `dynamodb:GetItem` / `BatchGetItem` / `PutItem` / `Query`: `articles` テーブルと GSI に限定
- `s3:PutObject`: サイト用バケットに限定

## 進め方

1. **ローカルで作る**: `store.py` の分離、`site.py`、Discord の削除。`uv run awsnews --site data/site/index.html` で書き出し、ブラウザのスマホ表示で確かめる
2. **AWS に載せる**: CDK でデプロイし、パスワードを登録する。Lambda を手動で 1 回起動し、実機のスマホで開けることを確かめる
3. **仕上げ**: 以下は必要になってから

- ホーム画面に追加できるようにする（PWA のマニフェスト）
- 30 日より前の記事のアーカイブページ
- 実行失敗の通知（CloudWatch アラーム）。まずは画面の「最終更新」で止まったことに気づける状態にしておく

## 決めておきたいこと

- 更新の時刻と回数（案: 9:00 / 18:00 の 1 日 2 回）
- トップに並べる期間（案: 直近 30 日）
